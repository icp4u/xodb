# M2 progress: profiling and static function navigation

M2 now includes static function navigation and bounded CPU sampling with native
flame graphs. See [PROFILING.md](PROFILING.md) for the P/F capture demo, source and
assembly links, MCP filters, test results and limitations. Grok's T06 collector
is integrated; T04 workloads and T07 active-layout input are also delivered.
DWARF function-range recovery and a normalized instruction inspection IR are
also available. [Basic Rust/Zig value views](M2_VALUES.md) now include slices,
byte/text previews, named enums and paged aggregate inspection. Tracing remains
pending. This is not the complete M2 acceptance gate.

## Try it

Run from your graphical session:

```sh
cd ~/Work/xodb
./scripts/build
./zig-out/bin/xodb --break flow_fixture --source tests/fixtures/m2.c \
  -- ./zig-out/bin/xodb-m2-fixture
```

1. **Space** continues from the exec stop to `flow_fixture`.
2. Press **G** or click **Flow**. The center pane shows address-ordered basic
   blocks with branch connections. Scroll with the wheel over that pane.
3. Click a block. Its source line gets a blue diamond and the header says
   **SOURCE / browsing**. The details below the graph show its outgoing edges
   and initial instructions.
4. Press **G** again to inspect assembly starting at the selected block.
5. Select a stack frame or step/continue to return to execution-based selection.
   **Q** closes xodb and cleans up the fixture.

Clicking a block does not execute code or change registers. The gold **PC** label
marks the block containing the actual stopped instruction pointer. Locals and
registers remain those of the selected stopped thread/frame; browsing a different
block does not predict its future values. Gold arrows in source mark the selected
execution frame; blue diamonds mark browsing.

Taken branches are green and not-taken branches orange. Other resolved edges
are blue; outgoing edges from the selected block are brighter. Call continuations
are explicitly **assumed**. Dim blocks have no path found through resolved edges
and assumed call returns; indirect transfers can still reach them.

## MCP inspection

`get_function_graph` is available in observe scope while stopped. Supply exactly
one selector: a hexadecimal `address` inside a function, or an ELF `symbol`.
Optional `generation` rejects a stale snapshot. Paginate with `start_block` and
`limit` (default 8, maximum 16):

```json
{"name":"get_function_graph","arguments":{"symbol":"flow_fixture","limit":8}}
```

The result includes generation, image epoch, module ID, symbol, runtime/link
addresses, declared size and decoded byte count. Each block has source metadata,
instruction count and its terminator. Outgoing edges identify destination block
or unresolved/external destination, edge kind and assumptions. `next_block` is
null at the end; otherwise pass it as `start_block`, preserving `generation`.
Edges may refer to blocks on another page. Symbol/source strings are capped at
512 bytes with explicit truncation flags.

`execution_observed` is always false. This graph describes decoded possibilities;
it contains no branch counts or profiling measurements. The
`reachable_via_resolved_edges` field follows resolved local transfers and assumed
call returns, excluding call-to-callee edges.

## Bounds and limits

- One contiguous compiler-declared function range, wholly inside one executable
  mapping. Prefer an ELF function symbol with a nonzero size. If it is absent or
  unsized, use the containing DWARF subprogram range. `extent_source` identifies
  `elf_symbol` or `dwarf_subprogram`; `range_index`, `range_count`, and
  `whole_function` expose split functions. Only the containing fragment is graphed.
  IFUNC symbols describe resolver code. Without ELF/DWARF bounds the operation
  remains unavailable; CFI rows, nearest names and prologue patterns are not
  treated as function boundaries.
- At most 64 KiB, 4,096 instructions and 512 blocks per function; exceeding a
  bound returns an explicit error. Decoding stops at the first invalid/truncated
  instruction and reports remaining bytes. Large functions are not silently
  truncated to satisfy those limits.
- Uses live stopped bytes with xodb software breakpoint bytes restored for
  decoding. Linear decoding can interpret embedded data as instructions.
  Indirect jump tables, overlapping instruction streams, exceptions, signals,
  transactional aborts and nonlocal transfers are not recovered.
- Direct branches resolve only to known instruction boundaries. External exits,
  indirect targets, non-boundary destinations, decode gaps, dynamic returns and
  function-end fallthrough remain distinct. A call may never return; its local
  continuation is an assumption. Reachability is not proof of execution.
- x86-64 decoding uses the existing Capstone dependency; no new dependency
  was added. The inspection IR described below normalizes operands
  and effects but does not execute instructions. ELF source lookup uses the existing libdw
  adapter. Static navigation is independent of T06/T07.
- The first layout is a scrollable column with routed edges, not a full graph
  editor. Selecting a block browses within the current function; following
  callees interactively and automatic layout remain future work.

## Instruction inspection IR

`get_instruction_effects` is an observe-scope query over stopped bytes, including
software breakpoint restoration. Required `address` is hexadecimal; optional
`generation`, `length` (1–1024, default 256), and `limit` (1–64, default 16) bound
work. It returns schema version 1, architecture, instruction addresses/sizes,
mnemonic/text, operation class, typed register/immediate/memory operands,
read/write access when available, implicit and explicit register accesses, and
raw prefixes. Memory operands include width, segment/base/index/scale/displacement.
RIP-relative static addresses are calculated only without a segment/index;
LEA operands are marked address expressions, never memory reads.

```json
{"name":"get_instruction_effects","arguments":{"address":"0x401000","length":128,"limit":16}}
```

Returned instruction addresses are integer target addresses. `next_address`
advances past the last decoded instruction; format it as hex for the next query.
`uninspected_bytes` and `instruction_limit_reached` distinguish the remaining
byte window from the instruction cap. Invalid/truncated trailing bytes are not
invented as instructions. Register aliases, flags, faults, REP/LOCK semantics,
and implicit memory effects remain architecture-specific. Every record explicitly
sets `semantics_complete=false` and `memory_effects_complete=false`; unsupported
operations are `opaque`. This is a normalized inspection layer for agents and
future analysis, not SSA, symbolic execution or a decompiler.
