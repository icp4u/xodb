# M1: source debugging and recorded experiments

The workstation baseline is implemented and validated on 2026-09-30. Follow
[README.md](../README.md#try-m1) for a manual GUI experiment. The scope is local
Linux x86-64 with ordinary C/C++ DWARF 4/5; the limits below remain explicit.

## What is connected

| Layer | Implementation |
| --- | --- |
| Binary identity | T01 ELF reader, mapped device/inode checks, explicit link/runtime addresses, lazy module loading |
| Debug information | Approved libdw adapter for lines, DIEs, types, locations and CFI; xodb evaluates target locations |
| Control | Software breakpoints with original-byte overlay/rearming, single step, source step/next, four hardware watchpoints, probe restoration on detach |
| Values | Scalars, pointers, records, one-dimensional arrays, simple C/C++ expressions and `$register` reads |
| Shared workspace | Source following/highlighting and gutter breakpoints, selectable frames, locals with shallow field expansion, registers and events |
| Agent coordination | Observe/control/mutate scope, mandatory generation on control, human revocation, tool-list notifications and action audit |
| Investigations | Question/expression, initial value, captured write events, frames/registers/locals, derived instruction/source attribution, JSON export |

The process backend remains local. Android and serial/network Linux debugging
are now explicit eventual goals in [MILESTONES.md](MILESTONES.md).

## The recorded answer: why did the value change?

The retained GCC DWARF 5 O0 experiment established:

1. Before continuing, `item->value` was **7** and a hardware write watchpoint
   covered its eight-byte address.
2. Event **16** stopped thread **2045** after a write. The sample changed from
   **7** to **12**. No other thread was running at that event.
3. The captured frame was `change_value`, called from `main` at the fixture's
   `FIRST_CALL`. Captured locals include `amount = 5` and `next = 12`.
4. Decoding forward from the ELF function start finds `mov qword ptr [rax], rdx`
   ending at the hardware-reported PC. Its source mapping is
   `tests/fixtures/m1.c:10`, `item->value = next`.

For this deterministic fixture, the evidence supports: the first call added 5
to 7 and assigned the resulting 12 to the watched field. The source highlight
at the stop is line 11 because execution has passed the store.

The record distinguishes the **observed** post-instruction PC and values from
the **derived** preceding instruction. It is not a recorded branch trace.
The `before` value is the previous debugger sample, not an atomic read just
before every write. Concurrent writers can change that interpretation; the
record retains `other_threads_running` and the sampling semantics.

## Manual and external-agent use

GUI: click a source line number to toggle its breakpoints; F11/F10 source-step
or step-over, with instruction fallback when there is no current source. Click
a frame to change the source/locals view. Click an addressable scalar or expanded
field in Locals and press W to start an investigation; W again removes that
address's watchpoint. Tab switches Locals/Registers. F8 toggles observe/control.

Local GUI expressions: **E** opens entry in the selected frame; **Return** adds
it to WATCH and **V** switches WATCH/EVENTS. With the watch list focused,
**Return** expands a structure/array/slice, **PgUp/PgDn** page children, **[ / ]**
or the wheel scroll, **Delete** (or **Backspace**) removes an entry, and **W** starts a hardware
write investigation. Watch entries keep their original context; they show stale
values while running and explicit unavailable/gone states. Later **CFA match**
results are a frame-matching heuristic, not proof of call lifetime. See the
[adopted T19 behavior and bounds](M2_EXPRESSION_WATCH_PROPOSAL.md).

MCP: use `get_session` to get `generation` and the Linux TID. Then:

1. `set_breakpoint` with `file`/`line` (returns every probe ID), or `symbol`.
2. `continue`, poll `get_session`, then `get_stack`, `list_locals`, and
   `evaluate_expression` at the desired `frame` (default 0).
3. `investigate_write` with `question`, `expression`, `tid` and generation.
4. `continue`, wait for the watchpoint, then `get_investigation` by its ID.
5. Remove probes when finished. `--record NEW_FILE` exports all investigations
   and the audit on application shutdown. It refuses to replace an existing file.

`control` permits execution/probe changes; `mutate` also permits explicit
memory/register writes. Both remain limited to the one target. Arbitrary calls
and shell expressions are unsupported. The same generation guard covers agent
commands even when a human is operating the GUI.

## Limits and next work

- One local x86-64 process/thread group. Worker exec, leader exit and attachment
  during thread creation are covered by the review regressions below. Fork/vfork
  trees and job-control/group-stop behavior remain unsupported; interrupting a
  parent blocked in vfork can time out until its child releases it.
- `.eh_frame` is the preferred CFI source; `.debug_frame` is the fallback.
  Signal frames are explicit `SignalFrameUnsupported`. Caller-clobbered
  registers may be unavailable. C++ names are not demangled yet.
- Split DWARF, separate debug-file search, type units, composite/piece locations,
  entry-value reconstruction, bitfields, inheritance, casts and richer language
  semantics are pending. Compressed `.debug_addr` indexed locations are not
  supported by the xodb location adapter. Other unsupported forms/operations
  yield diagnostics, not guessed values.
- Expression calls/assignments are rejected. `&&`/`||` are explicitly unsupported
  until lazy evaluation preserves short-circuit behavior. Integer arithmetic
  checks overflow; this is a basic debugger evaluator, not a complete C compiler.
- Source breakpoints resolve current mappings only. Matching a relative source
  suffix can select multiple addresses; returned IDs expose each one. Source
  contents are loaded from the local path and capped at 1 MiB with a visible
  truncation notice; source remapping
  and embedded source snapshots remain future work.
- Source stepping advances instructions, with a 10,000-instruction limit and
  human interrupt. Step-over runs other threads while a call executes; another
  stop cancels that run-to-return. Indexed line stepping is future performance work.
- Four aligned x86 hardware slots, 128 software probes, 1024 threads, 4096 recent
  events, 256 recent audit actions. Each investigation stores at most 16 hits,
  16 frames and 64 locals per hit; truncation/capacity is explicit. The GUI expands
  at most eight fields one level deep. Large evidence exports may exceed the
  stdio response queue; the shutdown JSON export retains the whole record.
- Module/CU and symbol lookups are still linear. Fixture validation does not
  establish game/server-scale parsing, sampling, or UI latency. T05 supplies
  small-workspace measurements; profiling and indexing belong to M2 work.

## Review integration

On 2026-09-30, Codex integrated Grok's T03 findings and Claude's T05 patches.

### Target lifecycle

- Waiting and cleanup use known target TIDs; unrelated child exits and trace
  stops are neither consumed nor adopted.
- `PTRACE_EVENT_EXIT` marks a thread non-runnable while its final wait status is
  pending. Linux can delay that final status for an exited leader until workers
  finish. Memory/maps use a live stopped TID; the UI selects a surviving worker.
  A `thread_exiting` event carries the kernel's raw wait status; `exit` carries
  the final decoded exit code or negative terminating signal.
- Worker exec retains only the renamed survivor and its stable thread ID, drops
  stale peers, and invalidates old probes. The image epoch changes.
- Detached owned children are reaped by later session polls without target
  events or killing them. An object destroyed before a detached child exits
  cannot keep reaping; its embedding process must own that lifetime if it stays
  alive. The standalone debugger polls until shutdown, then Linux reparents.
- Attach now stops discovered threads promptly and rescans after all-stop.
  Stress testing reproduced a missed-thread race and an already-auto-seized
  clone returning EPERM; tracer/group checks distinguish that case from denial.
- Partial resume errors recompute actual thread state. Attachment to a group
  whose leader was already a zombie is also covered.

These choices follow the kernel lifecycle described in the
[ptrace manual](https://man7.org/linux/man-pages/man2/ptrace.2.html).
The broader fork/vfork/group-stop workflows remain future work.

### T07 follow-up: Continue after Pause

T07 review reproduced a target-control defect through headless MCP: Continue,
Pause, Continue could leave the process stopped again. The target now tracks
outstanding interrupt requests per thread, preventing duplicate requests while
waiting for stops. Auto-attached newborn threads already have a pending stop.
An eight-cycle repeated-pause/resume regression and an attach/resume check pass;
so do the M1 control and stepping scripts. Run Claude's original repro with:

```sh
python3 tests/stale-interrupt.py
```

Expected states are `running`, `stopped`, `running`. This fix is independent of
the T07 input-policy decision. Exact evidence is in [journal.md](journal.md).
